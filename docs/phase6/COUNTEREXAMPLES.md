# Counterexamples

`crates/commitrift-model/src/witness.rs`, `report.rs`, `html.rs`.

## From schedule to witness

The explorer produces only a **schedule**: the sequence of transitions
`(kind, actor, task)` that leads to the violating state. The witness is
regenerated by **replaying** that schedule through the model with recording
on: every line of a witness is an event of a transition the model executed —
nothing is written by hand or templated per scenario.

Replay is strict: each transition must be enabled when taken, otherwise the
schedule is rejected (`an_invalid_schedule_is_rejected_by_replay`). For a
`final` invariant the schedule is completed to quiescence by running the
lowest enabled task step (never an optional crash or retry) and the
invariant is re-evaluated on the end state; for an `always` invariant the
schedule is cut at the first violating state.

## Minimization

Greedy, with a budget, and every candidate is validated by replay:

1. delete single transitions (the remaining schedule is replayed and
   completed; a deletion changes *when* a task's next operation runs, never
   which operation it is) — accepted only if the same invariant is still
   violated and the schedule got shorter, or equally long with fewer context
   switches;
2. swap adjacent transitions of different tasks — accepted if it is valid,
   still violating, and reduces context switches.

The minimized schedule is replayed once more to build the witness. Nothing
is removed because it "does not appear in the final diff": a transition
disappears only if a schedule without it still reaches a violation
(`counterexamples_replay_and_minimized_witnesses_still_violate` checks
length and context switches never grow, for DFS, BFS and reduced search).

## Example

`commitrift model-check fixtures/concurrency/scenarios/inventory-oversell.json
--validate-postgres` (extracted from `fixtures/concurrency/project/src/purchase.ts`):

```
COUNTEREXAMPLE: inventory-oversell

Initial state:
  orders: (no rows)
  products: {id="product-1", stock=1}

Schedule (6 transitions, 2 context switches, minimized and replayed):

    1  B   SELECT products WHERE (@id = "product-1") → {id="product-1", stock=1}   [src/purchase.ts:8:25]
    1  B   CHECK (!_row1 or (_row1.stock <= 0)) → false                            [src/purchase.ts:12:7]
    2  A   SELECT products WHERE (@id = "product-1") → {id="product-1", stock=1}   [src/purchase.ts:8:25]
    2  A   CHECK (!_row1 or (_row1.stock <= 0)) → false                            [src/purchase.ts:12:7]
    3  A   UPDATE products SET stock = 0 WHERE (@id = "product-1") → 1 row        [src/purchase.ts:16:9]
    4  A   INSERT orders {id="order-A", product="product-1"} → 1 row               [src/purchase.ts:21:9]
    4  A   return (success)
    5  B   UPDATE products SET stock = 0 WHERE (@id = "product-1") → 1 row        [src/purchase.ts:16:9]
    6  B   INSERT orders {id="order-B", product="product-1"} → 1 row               [src/purchase.ts:21:9]
    6  B   return (success)

Final state:
  orders: {id="order-A", product="product-1"}
  orders: {id="order-B", product="product-1"}
  products: {id="product-1", stock=0}

Invariant `successful-purchases-within-initial-stock` (final state):
  purchase:ok <= initial(products[id="product-1"].stock)
    purchase:ok = 2
    initial(products[id="product-1"].stock) = 1

Result:
  VIOLATED
```

`_row1` is the extractor's name for the `product` local. Full outputs (text,
JSON, HTML) are in `reports/phase6/model-check/`.

## Evidence levels

| Level | Meaning | Produced by |
| --- | --- | --- |
| model counterexample | a schedule of the model violates the invariant | `model-check` |
| PostgreSQL-confirmed schedule | the same schedule replayed on PostgreSQL in lockstep: every statement outcome (rows, counts, SQLSTATEs, blocking and by whom) matched, and the final committed rows are identical. The summary says whether the invariant reads only committed rows (then it is violated on the server) or also actor outcomes / external effects, which come from the model's application logic | `model-check --validate-postgres` |
| PostgreSQL did not reproduce | the first disagreement is reported as observed; the result must not be described as a race | same |
| runtime-reproduced invariant violation (original application code) | **not produced in Phase 6** — would need the application itself under controlled scheduling (the Phase 4 harness runs one request at a time) | — |
| inconclusive runtime verification | validation requested but PostgreSQL unavailable or the run failed | same |

A model counterexample is **not** a confirmed application bug: the scenario
chooses the actors, data, isolation level and bounds, and whether those
requests really run concurrently in production is not known.

## Report

Diagnostic codes of the concurrency category (separate from CP1001–CP9001,
which are not reused): `CP7001` invariant violated by a bounded schedule,
`CP7002` inconclusive (resource limit), `CP7003` unsupported behavior
reachable, `CP7101` PostgreSQL did not reproduce, `CP7102` validation
unavailable (`commitrift explain CP7001`).

The JSON report (`kind: "commitrift.model-check"`, `schemaVersion: 1`,
schema `docs/phase6/schemas/model-check-report.v1.schema.json`) contains:
model version, scenario version and file, source revision (when given),
actors with arguments, process, origin and source references, schema and
initial rows, declared bounds and whether reduction ran, verdict,
completeness, truncation flags, metrics, unsupported operations, every
invariant with its status, the witness, the evidence level and summary, the
runtime comparison, every modeling assumption, and diagnostics.
Serialization is deterministic (no timestamps; ordered maps; timing in a
separate object omitted by `--no-timing`; tested byte-for-byte).

The HTML view (`--format html`, or `commitrift report <json>`) is a
script-free page with a CSP that forbids scripts and remote resources, every
string escaped (tested with markup in scenario names and row values). It
draws the concurrent timeline — one column per request, plus an environment
column for crashes — with transaction boundaries, blocking, commits,
rollbacks, crashes, retries, deadlock victims and the violated invariant,
and, after `--validate-postgres`, PostgreSQL's observation next to each
transition.
