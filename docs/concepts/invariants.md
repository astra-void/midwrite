# Invariants and properties

A counterexample is only as meaningful as the property it violates.
Midwrite never infers a business invariant silently: every property is
either written by a person, enforced by the schema, implied by a declared
contract, or labeled a hypothesis.

## Assertion language (scenario invariants)

An invariant is data: `{ "name", "when": "final" | "always",
"description", "assert": <formula> }` (`crates/midwrite-model/src/invariant.rs`).
Formulas compare terms (`eq`, `ne`, `lt`, `le`, `gt`, `ge`) and combine
them (`and`, `or`, `not`, `implies`).

| term | value |
| --- | --- |
| literals | `3`, `"text"`, `null` |
| `initial` | a column of the initial row matching an equality filter |
| `row` | a column of the committed row matching a filter (`null` if none) |
| `count`, `sum` | committed rows matching a filter; sum of an integer column |
| `actors` | `ok`: successful completions of a function (a retried operation that succeeds twice counts twice); `failed`/`crashed`: actors whose latest attempt ended so; with `"returned": v` only completions whose main task returned `v` |
| `externals` | performed (not deduplicated) external effects on a channel, or distinct keys |
| `app` | an in-process variable |
| `add`, `sub` | integer arithmetic |
| `returned`, `argument` | what an actor (`self` inside `forEachActor`) returned in its **latest** completed attempt, or a field of it; an actor's argument or its field — how a declared property names the row a call works on without knowing synthesized values |
| `field` | a column of the row bound by `forEachRow` |
| `countMatching`, `rowMatching` | committed rows of a table matching a literal `where`, whose columns equal each `match` term (by identity for generated values), optionally `insertedBy` an actor selector; or a column of the first such row in key order |

The state an invariant reads is the **committed** database (uncommitted
versions are invisible), actor outcomes and return values, the
external-effect log and in-process variables. A comparison involving `null`
is false, except `eq`/`ne` against `null`; comparisons of two generated
values with `eq`/`lt`/… are false (use the identity formulas below).
`final` invariants are evaluated in quiescent states where every task
finished; `always` invariants in every reachable state (DPOR is refused
with them). See [model semantics](model-semantics.md#quiescence-termination-stuck-states).

Example ("at most one caller is told it claimed the task"):

```json
{ "le": [ { "actors": { "function": "claimTask", "outcome": "ok", "returned": true } }, 1 ] }
```

Return values are recorded only when an invariant reads them, so scenarios
without such an invariant keep their state spaces. An invariant over the
return value of an actor whose return expression is not modeled is
refused, never approximated. An `actors.function` names an entry actor by
its export's name.

### Generated identity and quantifiers

Formulas over generated identifiers state identities without fabricating
concrete values ([value semantics](value-semantics.md#generated-values)):

| formula | meaning |
| --- | --- |
| `generatedBy {value, by?, generator?}` | the value is a generated **identifier** (not a clock reading) whose generation event belongs to the selected actor(s) and generator |
| `sameGenerated [a, b]` | both are identifiers of the **same** event |
| `distinctGenerated [a, b]` | both are identifiers of **different** events (false when either is not generated: not the negation of `sameGenerated`) |
| `same [a, b]` | both present (not `null`/`undefined`) and equal; a generated value equals only itself |
| `forEachActor {function?, completed?, assert}` | holds for every actor running `function` (default: those whose main task completed at least once), bound as `self` |
| `forEachRow {table, where?, assert}` | holds for every committed row matching the filter, bound for `field` |

Selectors: `"self"`, `{"actor": "A"}`, `{"function": "f"}`. Generators:
`"call"` (any package call with a fresh-value contract; call sites are not
distinguished) or `{"column": "t.c"}` (that column's generated default,
validated).

Precise rules:

* A generated value copied into several places (a key and a foreign key, a
  local, a returned object) is the same event everywhere.
* "Generated by actor A" means **any** of A's generation events of that
  generator, not a specific occurrence: the occurrence counter shifts with
  retries and the actor's other generators. Properties that must tell
  attempts apart say so through the data ("the returned id is the id of a
  row inserted by the same actor": `countMatching` with `match` and
  `insertedBy`, false for an id whose insert was rolled back).
* `null`/`undefined` are never `same`, never generated, and a `match` term
  that evaluates to either selects no row. A row's inserting actor is the
  actor of its logical row id; initial rows match no `insertedBy`.
* Quantifiers range over the model's actors and committed rows and nest;
  a quantifier over nothing holds. There is no quantifier over generation
  events or attempts.
* Validation at load time rejects unknown tables, columns, actors,
  functions and arguments, `self`/`returned` outside their scope, `field`
  outside `forEachRow`, a generator column without a generated default, and
  unknown fields.

When such an invariant is violated, the witness's final summary carries a
**diagnosis** per failing identity predicate: `generated-identity
mismatch` (identifiers of another event, actor or generator), `absent
value` (with the `replicas` feature it adds that a read that has not
observed a write returns this, which eventual consistency permits unless a
property requires visibility), or `not a generated value of the expected
identity`. The diagnosis classifies values, not their cause; the schedule
shows whether a `replicate` step happened.

Which actor generated a value is not observable in an original-code run,
so a property using these formulas is reported `not-evaluated` on original
code — never held or violated there.

## Property origins

`discover` attaches property candidates; each has an origin that no later
step changes ([scenario synthesis](../architecture/scenario-synthesis.md)).

| origin | meaning | how a counterexample is reported |
| --- | --- | --- |
| `SCHEMA_ENFORCED` | a supported, non-partial unique constraint covers the property | the property is enforced by the schema |
| `USER_DECLARED` | written in `midwrite-contracts.json` | declared by the user |
| `FRAMEWORK_CONTRACT` | follows from a declared integration contract (at-least-once delivery ⇒ at most one effect per message) | implied by a declared contract |
| `HEURISTIC_HYPOTHESIS` | suggested by the code, not established | "MODEL_COUNTEREXAMPLE against a HEURISTIC_HYPOTHESIS … not a confirmed defect" |
| `SOURCE_ASSERTED` | an explicit assertion in source with a stated translation | defined; no rule produces it |

A missing constraint is not evidence that uniqueness was intended; a
partial unique index is reported as a protection, never as
`SCHEMA_ENFORCED`. Each emitted scenario's invariant description starts
with its origin, so it travels into `model-check` reports.

## Templates

Declared invariants (`midwrite-contracts.json`, [contracts](../user-guide/contracts.md))
and synthesized properties use templates: `atMostOne {table, key, where}`,
`atLeast {table, groupBy, where, min}`, `nonNegative {table, column}`,
`maxExternal {channel, max}`, `formula` (a literal assertion), the
return-value templates `atMostOneSuccess`, `exactlyOneSuccess`,
`everySuccessReturns`, plus the synthesized `serialCell` and
`noFailedActors`. Eventual properties ("an event is eventually published")
are not synthesized.

### `serialCell`

The `HEURISTIC_HYPOTHESIS` of read-modify-write candidates: "the cell ends
with a value some serial execution of the same requests produces, for the
same number of completed requests". The engine runs the actors one after
another in every order and subset (no faults) and collects, per completed
count *k*, the cell's values *V_k*; the property is `OR_k (completed = k AND
OR_{v ∈ V_k} cell ≈ v)`.

* `cell ≈ v` is equality for integers, strings and `null`; for a generated
  identifier it is `generatedBy(cell, by: A, generator: G)` **when the
  renaming is faithful** — actor A's code has exactly one generation site of
  G and no backward jump, so "A's value from G" denotes the same program
  point in the serial and the concurrent run (with retries, any attempt's
  value at that site is accepted; stated in the description). Booleans,
  rows, clock readings and unfaithful identifiers are refused with a note,
  never assigned arbitrary values.
* With the `replicas` feature, serial executions explore every choice of
  replica progress at every step (bounded; beyond the bound the property is
  not instantiated, with a note), so a stale or a fresh read alone never
  violates the heuristic property.

## Properties that need a declaration

* Write skew (multi-row invariants) — `BLOCKED` without one; a candidate's
  existence does not imply an invariant.
* Return-value properties ("at most one caller told `true`",
  read-your-writes, freshness of a replica read): no heuristic infers them,
  which is why observable positives on the evaluation sets can be false
  negatives ([evaluation methodology](../research/evaluation-methodology.md)).
* Recovery requirements (an event is not lost, a payment is eventually
  recorded): never synthesized.

## Appendix: contract templates

Midwrite never infers a multi-row invariant, so midday's three
write-skew candidates stay BLOCKED until a developer declares one. These
are **templates, not findings**: each states a business rule that midday's
code does not state, and is correct only if it is the developer's rule.
Copy the chosen objects into the `invariants` array of a
`midwrite-contracts.json` ([contracts](../user-guide/contracts.md)), adjust names,
values and entries, and rerun `midwrite discover --model-check
--contracts FILE`. The selectors are midday's (commit `51587319`); the
templates use only the real declaration syntax. Test
`every_contract_template_parses_and_loads_against_the_first_party_application`
(`crates/midwrite-discover/tests/generated_ids.rs`) parses every block
below as a contracts file, points its entries at the midday-shaped code of
`fixtures/apps/genid` (same table and column names), runs discovery and
checks that the property attaches to a candidate and is model-checked.

### Team membership (`leaveTeam`, `deleteTeamMember`: write skew on `users_on_team`)

A team keeps at least one owner. Choose it if removing the last owner
must be impossible; a concurrent `leaveTeam` of two owners is then the
write skew the candidate describes.

```json
{
  "name": "team-keeps-an-owner",
  "description": "Every team that has members keeps at least one member with the owner role.",
  "entries": [
    "packages/db/src/queries/teams.ts#leaveTeam",
    "packages/db/src/queries/teams.ts#deleteTeamMember"
  ],
  "property": {
    "template": "atLeast",
    "table": "users_on_team",
    "groupBy": ["teamId"],
    "where": { "role": "owner" },
    "min": 1
  }
}
```

(`atLeast` is instantiated per group of the synthesized initial rows; a
group that violates it in the initial state is not checked, with a note.)

A user's current team is one they belong to (`forEachRow` and
`countMatching`). Choose it if `users.teamId` must always name a
`users_on_team` membership of that user. It is declared for `leaveTeam`
only: a synthesized scenario contains the tables its actors use, and
`deleteTeamMember` never touches `users`, so for it the loader refuses the
formula (`unknown table \`users\``, verdict `NOT_LOADED`, measured on the
fixture). Note that `deleteTeamMember` leaves `users.teamId` unchanged, so
under this rule it is a defect even without concurrency.

```json
{
  "name": "current-team-is-a-membership",
  "description": "A user's current team (users.teamId) is null or a team the user is a member of.",
  "entries": [
    "packages/db/src/queries/teams.ts#leaveTeam"
  ],
  "property": {
    "template": "formula",
    "assert": {
      "forEachRow": {
        "table": "users",
        "assert": {
          "or": [
            { "eq": [{ "field": "teamId" }, null] },
            {
              "ge": [
                {
                  "countMatching": {
                    "table": "users_on_team",
                    "match": { "userId": { "field": "id" }, "teamId": { "field": "teamId" } }
                  }
                },
                1
              ]
            }
          ]
        }
      }
    }
  }
}
```

### Insight generation (`GenerateInsightsProcessor.process`: write skew on `insights`)

Every completed job reports an existing insight (`forEachActor`,
`returned`, `countMatching`; the insight's id is database-generated).
Choose it if a job's `insightId` must name the period's stored insight.

```json
{
  "name": "insight-job-reports-a-stored-insight",
  "description": "Every completed insight job that reports an insightId reports the generated id of a stored insight.",
  "entries": [
    "apps/worker/src/processors/insights/generate-team-insights.ts#GenerateInsightsProcessor/method[process]"
  ],
  "property": {
    "template": "formula",
    "assert": {
      "forEachActor": {
        "assert": {
          "implies": [
            { "ne": [{ "returned": { "path": "insightId" } }, null] },
            {
              "eq": [
                { "countMatching": { "table": "insights", "match": { "id": { "returned": { "path": "insightId" } } } } },
                1
              ]
            }
          ]
        }
      }
    }
  }
}
```

A duplicate job does not fail. Choose it if two jobs for one period may
overlap and neither should end in "Failed to create insight record" (the
`ON CONFLICT DO NOTHING` of the second job's insert returns no row).

```json
{
  "name": "insight-jobs-do-not-fail",
  "description": "No insight job fails.",
  "entries": [
    "apps/worker/src/processors/insights/generate-team-insights.ts#GenerateInsightsProcessor/method[process]"
  ],
  "property": {
    "template": "formula",
    "assert": { "eq": [{ "actors": { "outcome": "failed" } }, 0] }
  }
}
```

"At most one insight per team and period" needs no declaration: the
`insights_team_period_unique` constraint enforces it (a `SCHEMA_ENFORCED`
property).
